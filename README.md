# Комната ПЭЗ. Digital

Запускаемый scaffold для цифрового контура продукта PRODEX: анонимизированный маршрут тестирования «до / после», персональный отчёт участнику и агрегированная аналитика работодателю.

## Быстрый старт

```bash
copy .env.example .env
docker compose up --build
```

- Frontend: http://localhost:5173
- Backend health: http://localhost:8000/api/health/
- Django admin: http://localhost:8000/admin/

Чтобы пройти маршрут участника локально (вход → согласие → вопросы), нужен корпоративный код и
опросник:

```bash
docker compose exec backend python manage.py seed_demo_organization
docker compose exec backend python manage.py seed_real_questionnaires
```

Вторая команда загружает реальные методики — EQ-5D, Госпитальную шкалу тревоги и депрессии (HADS)
и шкалу самооценки тревожности Спилбергера–Ханина — с вопросами, вариантами ответа, ключами
и границами зон интерпретации из методички методолога (60 вопросов суммарно: 5 измерений EQ-5D +
VAS, 14 HADS, 40 СШХ). Есть и упрощённая заглушка (`manage.py seed_dummy_questionnaire`, 6 вопросов,
без реальных ключей) — для быстрой проверки маршрута без реальных данных; по умолчанию активен
комплект из `seed_real_questionnaires`.

Первая команда выводит `entry_code` — откройте `http://localhost:5173/?code=<entry_code>`.

Реализован маршрут участника FR-01…FR-04, FR-06…FR-08 (вход по коду, согласие, автоопределение
этапа, прохождение вопросов с автосохранением, автоматический scoring и персональный отчёт
«до / после»), дашборд работодателя FR-09 (охват, completion, 5 групповых показателей
«вход/итог», фильтр по потоку, скрытие малых групп) и экспорт PDF/XLSX FR-10 — всё это открывается
на `http://localhost:5173/employer` (desktop, без мобильной адаптации) за лёгким логином
(логин/пароль сотрудника, не полноценный RBAC — см. ниже).

PRODEX Admin FR-11 — на `http://localhost:5173/prodex`, отдельный контур от дашборда работодателя
(ТЗ FR-11.6): таблица клиентов со статусом лицензии и фильтрами (FR-11.2/11.3), потоки, completion,
активность и ошибки подсчёта как технические метрики (FR-11.4), без единого психологического
показателя участника (FR-11.5). Доступен только администратору PRODEX — администратор организации
получает отказ (FR-11.1, `apps/identity/permissions.py::IsProdexAdmin`). Полный RBAC с
разграничением действий внутри контуров (ТЗ FR-12, помимо уже готовой изоляции организаций и
audit log) ещё не реализован — см. `project/ROADMAP.md` и `project/TEST_SCENARIOS.md`.

Чтобы на дашборде было что посмотреть (помимо `demo-stream`, который наполняется тестовыми
прохождениями всего проекта и потому не показателен) и залогиниться, выполните:

```bash
docker compose exec backend python manage.py seed_employer_demo_streams
docker compose exec backend python manage.py seed_demo_staff
docker compose exec backend python manage.py seed_demo_licenses
```

Первая создаёт поток `2026-H2` у демо-организации (8 участников — выше порога публикации, обычный
вид) и поток `2026-pilot` у организации «ООО Вектор Плюс» (3 участника — ниже порога, демонстрирует
скрытие маленькой группы). Третья выдаёт демо-лицензии (ТЗ FR-11.3): активную демо-организации и
истёкшую «ООО Вектор Плюс» — чтобы на экране PRODEX Admin было видно оба статуса. Вторая печатает
пароль и заводит три учётки:

- `hr_demo` — администратор организации, видит только демо-организацию;
- `coordinator_demo` — администратор организации, видит только «ООО Вектор Плюс»;
- `prodex_demo` — администратор PRODEX, видит все организации.

Ролей по «Положению о пользовательских ролях» три: участник, администратор организации и
администратор PRODEX (см. `project/PRODUCT_SPEC.md`). Участник в `identity.StaffProfile` не входит —
у него нет логина вообще, доступ управляется владением токена. Администратор организации привязан к
своему юрлицу и видит только его, администратор PRODEX — все. Это ещё не полноценный RBAC из
ТЗ FR-12: разграничения действий внутри контура нет, журналируются только входы и выгрузки
(`apps/identity/views.py`, `apps/identity/permissions.py::IsStaffMember`). Контур PRODEX Admin
(`/prodex`) разграничен по роли отдельным пермишеном — `IsProdexAdmin` — администратор организации
получает туда 403.

## Работа с GitLab

В проекте используется одна основная ветка `main`. Прямые изменения в `main` не выполняются.

### Правила ветвления

- Каждая доработка выполняется в отдельной ветке, созданной от актуальной `main`.
- Для новой функциональности используется формат `feature/<краткое-описание>`.
- Для исправления ошибки используется формат `fix/<краткое-описание>`.
- Для технических изменений используется формат `chore/<краткое-описание>`.
- Перед началом работы необходимо обновить локальную `main`:

```bash
git switch main
git pull origin main
```

- Новая ветка создаётся от обновлённой `main`:

```bash
git switch -c feature/<краткое-описание>
```

### Merge Request

- Завершённая доработка отправляется в GitLab и вливается в `main` только через Merge Request.
- В Merge Request нужно указать цель изменения, основные изменения, способ проверки и известные ограничения.
- Перед созданием Merge Request необходимо синхронизировать ветку с `main`, разрешить конфликты и проверить проект локально.
- Merge Request должен проходить code review и обязательные CI-проверки.
- В `main` вливаются только проверенные изменения, готовые к дальнейшей разработке или релизу.
- После успешного слияния рабочая ветка удаляется в GitLab и локально.

### Рекомендуемый цикл работы

```bash
git switch main
git pull origin main
git switch -c feature/<краткое-описание>

# работа над изменениями
git add .
git commit -m "feat: краткое описание изменения"
git push -u origin feature/<краткое-описание>
```

После отправки ветки создаётся Merge Request `feature/<краткое-описание>` → `main`.

Перед слиянием рекомендуется выполнить:

```bash
docker compose config
docker compose build
docker compose up -d
curl.exe -fsS http://localhost:8000/api/health/
docker compose down
```

После слияния локальная ветка удаляется:

```bash
git switch main
git pull origin main
git branch -d feature/<краткое-описание>
```

## Структура

- `backend/` — Django + DRF API.
- `frontend/` — React + TypeScript + Vite.
- `project/` — требования, правила, архитектура, privacy и roadmap.
- `docker-compose.yml` — локальная инфраструктура PostgreSQL, Redis, backend и frontend.

## Важные ограничения

- Не добавлять ФИО, телефон, e-mail или табельный номер в тестовый контур MVP.
- Работодатель получает только агрегаты; индивидуальные результаты ему не выдаются.
- Порог публикации малых групп и юридический режим обработки должны быть подтверждены до production.
- Версии и лицензии EQ-5D, Спилбергера–Ханина и HADS подтверждаются до релиза scoring.
